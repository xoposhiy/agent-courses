<a id="the-execute-tool"></a>


## The `execute` tool

Shell-capable backends expose an `execute(command)` tool. The agent calls it to run scripts it has written, invoke CLI tools, and compile and test code. The combined command output, exit code, and execution metadata come back as a tool result on the next LLM call.

---

<a id="how-do-you-choose"></a>


## How do you choose?

Two shell-capable backends are available: `LocalShellBackend` and sandbox backends. The deciding factor is isolation.

![LocalShellBackend runs code on the host; sandbox backends run code in an isolated container](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-localshell-vs-sandbox.svg)

**Use a sandbox.** Agent generated code and packages the agent may load are untrusted by nature. Use a sandbox to isolate that code from your infrastructure.

**Use `LocalShellBackend`** when building a local tool where the agent working directly on your machine is the point, such as a coding assistant or desktop agent. It is not appropriate for production or untrusted input.

<a id="sandbox-backends"></a>


## Sandbox Backends

A sandbox is a temporary, isolated workspace containing a filesystem, command execution environment, and other resources. Sandbox backends run commands inside that workspace instead of on your host machine.

There are two models for using a sandbox with an agent:

![Two sandbox models: agent in sandbox vs sandbox as a tool](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-models.svg)

**Agent in Sandbox:** The agent itself runs inside the sandbox. The LLM API key(s) live inside the sandbox. To update the agent, you must rebuild the sandbox image. This is useful when you want the execution environment to mirror your production infrastructure.

**Sandbox as a Tool:** The agent runs outside and calls the sandbox via `execute` and filesystem tools. The LLM API keys stay on your host, agent code is easy to update, and sandbox failures don’t affect agent state. This is the model used in this course.

<a id="managing-credentials-in-a-sandbox"></a>


### Managing credentials in a sandbox

Sandbox-as-a-tool keeps the LLM API key on the host, away from the untrusted code running in the sandbox. But an agent often needs other keys too, to reach services on the user’s behalf. LangSmith Sandboxes can attach those keys to outgoing requests without exposing them to the code the agent runs. The slideshow below shows how:

### Slideshow: ss-sandbox-flow

#### Step 1 of 6 · Isolation from the host

![Step 1 of 6 · Isolation from the host](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-1.svg)

The agent spawns sandboxed code away from the host isolating code execution.

#### Step 2 of 6 · The credential gap

![Step 2 of 6 · The credential gap](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-2.svg)

The External API box is whatever third-party service the code is trying to reach, such as Stripe or GitHub. A request has no credentials to send, and putting an API key inside the sandbox so it could send one would expose that key to the agent's own generated code.

#### Step 3 of 6 · Auth proxy sidecar

![Step 3 of 6 · Auth proxy sidecar](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-3.svg)

LangSmith Sandboxes add an auth proxy sidecar inside the sandbox boundary. It is a separate process from the code the agent writes, and for now it holds no secret either.

#### Step 4 of 6 · Code calls the proxy, not the API

![Step 4 of 6 · Code calls the proxy, not the API](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-4.svg)

Instead of calling the external API directly, the sandboxed code sends its request to the local proxy.

#### Step 5 of 6 · Secret injected into the proxy

![Step 5 of 6 · Secret injected into the proxy](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-5.svg)

Separately, the proxy is provisioned with the real credential from workspace secrets. The secret now lives in the proxy, still inside the sandbox boundary, but in a separate process.

#### Step 6 of 6 · Auth proxy closes the gap

![Step 6 of 6 · Auth proxy closes the gap](../../raw/repositories/lca-deepagents/thinkific/src/m2/images/m2.3-sandbox-flow-6.svg)

The proxy attaches the credential and forwards an authenticated request to the external API. Isolation keeps the code away from the host. The auth proxy keeps the secret away from the code.

The auth proxy pattern above is specific to LangSmith Sandboxes. The proxy sidecar holds the secrets inside the sandbox, but the code the agent writes and runs never sees them, so the code cannot exfiltrate them.

## LocalShellBackend

`LocalShellBackend` runs commands directly on the host machine. It can scope filesystem *tools* to a `root_dir`, but `execute` itself runs with host permissions; no process isolation is applied.

`virtual_mode=True` is the default: filesystem tools (`ls`, `read_file`, `write_file`, etc.) are path-scoped under `root_dir`, and paths resolving outside it are rejected. Pass `virtual_mode=False` to allow absolute host paths instead. Either way, `root_dir` does not restrict the `execute` tool. Shell commands run with host permissions and can access paths outside the filesystem-tool root. That’s why LocalShellBackend is unsuitable for production or untrusted input.

In TypeScript, `virtualMode` defaults to `false` (unlike Python), so pass `virtualMode: true` explicitly: filesystem tools (`ls`, `read_file`, `write_file`, etc.) are then path-scoped under `rootDir`, and paths resolving outside it are rejected. ⚠ Security Warning

This backend grants agents direct filesystem read/write access and unrestricted shell execution on your host. Use with extreme caution and only in appropriate environments.

**Appropriate use cases:**

- Local development CLIs (coding assistants, development tools)
- Personal development environments where you trust the agent’s code
- CI/CD pipelines with proper secret management

**Inappropriate use cases:**

- Production environments (such as web servers, APIs, multi-tenant systems)
- Processing untrusted user input or executing untrusted code

**Security risks:**

- Agents can execute arbitrary shell commands with your user’s permissions
- Agents can read any accessible file, including secrets (API keys, credentials, `.env` files)
- Secrets may be exposed
- File modifications and command execution are permanent and irreversible
- Commands run directly on your host system
- Commands can consume unlimited CPU, memory, disk

**Recommended safeguards:**

- Enable Human-in-the-Loop (HITL) middleware to review and approve operations before execution. This is strongly recommended.
- Run in dedicated development environments only. Never use on shared or production systems.
- Use a sandbox backend for production environments requiring shell execution.

**Note:** `virtual_mode=True``virtualMode: true` provides no security with shell access enabled, since commands can access any path on the system.

## Recap

- `execute` is added by shell-capable backends on top of the standard filesystem surface
- **LocalShellBackend:** no process isolation, for controlled local development only
- **Sandbox backends:** isolated from the host when configured correctly; multiple providers are available, and this course uses LangSmith
- The filesystem tool surface is consistent; `execute` is available when the backend supports shell execution

**⚠ Troubleshooting timeouts:** raising the model’s `timeout=` (set in `models.py`) won’t help; it only bounds the LLM API call, not sandbox operations. Sandbox timing has separate knobs:

- Sandbox creation waits up to 30s for the sandbox to become ready (`client.create_sandbox(…, timeout=30)`), then raises a resource-timeout error.
- `execute` defaults to a 30-minute overall command timeout.
- Its idle timeout defaults to 5 minutes: a command that produces no output for that long gets killed, even if it’s nowhere near the 30-minute limit.

This lab’s `pip install` plus chart generation is the most likely to hit the idle timeout. Check the LangSmith trace for the specific error before assuming the model’s `timeout=` is the cause.
