Long-horizon problem solving and scientific research require computation to accumulate across succes-
sive attempts. Partial solutions, experimental findings, and even unsuccessful approaches can become
useful to later work, yet most inference-time computation is organized around individual trajectories or
candidates rather than a persistent body of reusable work. We call this paradigm compounding infer-
ence: organizing inference-time computation so that intermediate work persists and can be inspected,
extended, combined, or challenged by subsequent computation. We instantiate compounding inference
in GitSwarm, an asynchronous system in which homogeneous agents independently decide how to
advance a task while collaborating through structured persistent memory. Agents explore, experiment,
verify, refine, and synthesize previous work in a shared, branchable Git repository. Atomic commits
preserve intermediate artifacts, while explicit semantic dependencies record how later contributions
build on work across branches. We evaluate GitSwarm on long-horizon problem solving and sustained
GPU-backed experimental research. On IMOProofBench-Advanced, GitSwarm solves all 30 problems
in one run using GPT-5.5. On ProgramBench, it achieves a 79.4% mean score, compared with 65.1%
for the strongest reported baseline under the stated budget. Across three neural architecture research
tasks: Residual Matrix Transformer, Looped Transformer, and NanoChat, GitSwarm improves upon
the respective starting architectures through successive experimentation. Beyond final performance,
we measure whether computation actually accumulates: on ProgramBench, 94.7% of contributions
are subsequently built upon, while the selected solution’s transitive ancestry covers 82–93% of the
contribution graph. Together, these results show that inference-time computation can accumulate
across otherwise independent episodes, forming an evolving body of work that subsequent inference
can reuse.

Introduction

Scaling inference-time computation improves language model performance through repeated sampling, longer
reasoning trajectories, search, and multi-agent collaboration (Brown et al., 2024; Snell et al., 2024; Du et al.,
2023). These approaches largely ask how additional computation should be spent. Long-horizon problem
solving and scientific research pose a complementary challenge: useful computation must also accumulate
across attempts.

The value of intermediate work is often unknown when it is produced. An unsuccessful experiment may reveal a
promising direction; a partial solution may establish an ingredient used much later; competing approaches may
contain ideas that become useful only when combined. If such work disappears when an episode terminates,
later computation may need to rediscover it. Preserving it instead allows subsequent agents to build on an
accumulated body of prior work. We call this paradigm compounding inference: organizing inference-time
computation into a persistent, evolving body of reusable work.

Existing approaches support different parts of this process. Independent sampling explores diverse candidates,
longer reasoning trajectories retain work within an episode, and multi-agent systems enable collaboration,
often through predefined roles, centralized planning, or shared conversations (Hong et al., 2024; Chen et al.,

We instantiate compounding inference in GitSwarm, which uses a shared, branchable Git repository as
structured persistent memory. Homogeneous workers operate asynchronously, inspect previous contributions,
and independently decide whether to explore, experiment, verify, refine, or combine existing work. Each
contribution is published as an atomic commit. Importantly, GitSwarm distinguishes the repository state
from which a worker begins from the additional prior contributions that its work depends on. Explicit semantic
dependencies therefore allow a worker to extend one branch while drawing on discoveries from others. This
preserves competing approaches without losing the connections between them. No central intellectual planner
assigns tasks or roles; an execution harness manages scheduling and validation, while workers nominate
candidates for final selection.

Our evaluation spans two settings. The first is long-horizon problem solving, where tasks have well-defined objec-
tives and verifiable outcomes. We study mathematical proof and program reconstruction. On IMOProofBench-
Advanced (Luong et al., 2025), GitSwarm solves all 30 problems in one run using Codex (GPT-5.5-High)
workers and slightly under one million output tokens. On ProgramBench (Yang et al., 2026), with Codex
(GPT-5.5-High) workers, it achieves a 79.39% mean score, as compared to 65.12% for Forced Codex - a single
Codex (GPT-5.5-High) agent repeatedly prompted to continue, at a comparable compute budget. Mean
performance improves with inference-time computation over the tested ranges.

that guides subsequent computation.

reusable inference-time computation across episodes; we introduce GitSwarm as a concrete realization based
on persistent, branchable contributions with explicit cross-branch dependencies; and we evaluate both task
performance and the accumulation process itself across problem solving and sustained experimental research.

2
GitSwarm

GitSwarm implements compounding inference through asynchronous, homogeneous workers collaborating
over a shared Git repository. Workers independently decide how to advance the task, while an execution
harness manages concurrency, isolation, validation, and publication. The repository preserves intermediate
work as a branchable computation graph.

2.1
Design Principles

We seek to accumulate computation without prescribing how agents should organize their work.
This
requires three properties of the shared memory: persistence, so intermediate discoveries survive their authors;
branchability, so competing approaches can develop without prematurely committing to a single solution; and
attribution, so subsequent workers can identify dependencies between contributions, including across branches.
These properties support adaptive, decentralized control: workers independently choose what to explore, verify,
refine, or combine based on the evolving shared state. The harness coordinates execution but does not assign
intellectual roles or prescribe a sequence of problem-solving stages.

2.2
Shared Computation Graph

Consider a task q, a fixed language model pθ, and a budget of B charged worker episodes. For each task,
GitSwarm initializes a Git repository containing the task specification and required artifacts, committed as
an immutable root v0. Accepted contributions form an evolving graph Gt = (Vt, Et), where Vt = {v0, . . . , vt}
contains the root and the first t published contributions. Each contribution vi is an atomic Git commit with a
physical parent pi ∈Vi−1. This parent identifies the state from which the worker began, but need not capture
all the information used in its contribution.

To record additional dependencies, each worker declares a set of semantic sources Ui ⊆Vi−1 in a mandatory
informed_by= field. The physical parent must be included in Ui. The graph contains both Git-parent edges
and additional semantic-dependency edges:

Et = {(pi, vi) : 1 ≤i ≤t}

inherit one branch while using discoveries from others, without requiring merges. Semantic dependencies are

2.3
Asynchronous Worker Protocol

A run has a budget of B charged worker episodes and maximum concurrency C. The harness maintains up
to C active workers, launching replacements as slots become available. All workers use the same model and
behavioral contract, without predefined roles.

Each worker operates in an isolated Git worktree. It inspects the repository, selects a starting commit, and
independently decides how to advance the task. Each episode ends with one of three actions:

1. Contribute: Publish one validated, atomic commit containing new work, such as a partial solution,
experiment, test, or refinement. Validation enforces task-specific publication requirements, not solution
correctness.
2. Nominate: Select an existing candidate and publish a separate nomination record with a rationale, without
modifying the candidate.
3. Abstain: Terminate without publication when no useful additional work is identified or equivalent work is
already underway.

Voluntary abstentions trigger replacement without consuming B, although they incur inference costs; other
episode outcomes consume the budget. Workers may therefore allocate effort adaptively among exploration,
refinement, experimentation, verification, integration, and selection.

2.4
Live Swarm State: Dashboard and In-Flight Activity

Workers also see the current state of the run and what their peers are doing, through two interfaces that
report state but do not assign work (Figure 2).

Dashboard. Every worker receives a dashboard snapshot at spawn time and can query the live state with
gs_dashboard. It reports the remaining worker budget, the workers in flight, and the nomination tally, noting
that votes are not evidence of correctness. For research tasks, which use a wall-clock budget and select the
final model by validation score, the budget and nomination fields are replaced by shared GPU, CPU, and job
usage, a warning when GPU utilization is low, and the best validation score with its commit.

In-flight activity. Since uncommitted work is invisible in the repository, each worker keeps a public activity
log via gs_inflight. It announces its scope (gap, deliverable, success and abort criteria) before editing and
posts progress updates. Peers can list active workers or inspect a worker’s log and uncommitted changes, but
cannot modify them. This is meant to help workers avoid taking up work which is already being undertaken
by their in-flight peers.

3
Experiments

We evaluate GitSwarm in two settings: long-horizon problem solving and sustained experimental research.
We first measure benchmark performance and inference-time scaling on mathematical proof and program
reconstruction. We then study three GPU-backed architecture research tasks. Finally, we examine reuse,
transitive accumulation, and adaptive coordination. Controlled synthetic tests (Appendix C) and architectural
comparisons probe individual system properties.

3.1
Experimental Setup

Problem-solving tasks. IMOProofBench-Advanced (Luong et al., 2025) contains 30 mathematical proof
problems. ProgramBench (Yang et al., 2026) asks agents to reconstruct programs from documentation
and an execute-only reference. We evaluate all 30 proof problems and a fixed subset of 50 ProgramBench
tasks, stratified by language, difficulty, test-suite size, and runtime (Appendix B.2). We use nine separate
programming tasks and six proof problems during development; the latter are included in the full proof
evaluation. Scoring rules and task selection are detailed in Appendix B.1.

Models and baselines. For IMOProofBench-Adavnced, we use GitSwarm with Gemini-3.1-Pro and GPT-5.5-
high workers. We compare against single agents using bash, mini-SWE-agent (Lieret and Jimenez, 2025),
or Codex (OpenAI, 2025) (as appropriate to the model), repeatedly prompted to continue after stopping.
For ProgramBench, we use Codex (GPT-5.5-high) workers and GPT-5.5 workers at the default reasoning
effort, and compare against a repeatedly continued Codex (GPT-5.5-high) agent. We always use a worker
concurrency of 5 for GitSwarm in the case of problem-solving tasks. We call these continued single-agent
baselines Forced and evaluate their intermediate natural stopping checkpoints.

Compute accounting. GitSwarm’s budget B counts charged worker episodes. Voluntary abstentions are
replaced without consuming the budget, although they still incur inference costs. Programming runs use
budgets of 100, 200, 300, and 500 episodes; proof runs use 20, 40, 80, 120, and 160. These measurements
account for differences in the amount of work performed within an episode.

We report performance scaling curves with respect to input and output token counts in the case of problem-
solving tasks. We count tokens per model request and sum them over all requests made by a worker or agent:
input tokens count the full prompt sent with each request, including all previously accumulated context.
Output tokens count only the tokens newly generated in that request, including hidden reasoning tokens.

3.2
Benchmark Performance and Inference-Time Scaling

We first test whether additional inference-time compute improves performance on tasks with well-defined
answers. We evaluate program reconstruction and mathematical proof, measuring both final performance and
how it changes as workers receive larger budgets.

ProgramBench. Figure 3 examines scaling on the 50 tasks shared by all plotted runs. With Codex workers,
GitSwarm improves from 73.1% with 100 workers to 79.4% with 500. With GPT-5.5 workers, it improves from
64.6% with 100 workers to 71.2% with 300. In comparison, the sequentially continued Codex baseline remains
between 63.1% and 65.1% across its plotted checkpoints. GitSwarm’s gains diminish at larger budgets, while
input-token costs grow as workers inspect an expanding repository.

IMOProofBench-Advanced. We next test whether scaling also helps on mathematical proof problems. With
Gemini-3.1-Pro, the mean number of fully correct proofs increases from 23.3 at a budget of 20 workers to
29.0 at 160. The curve is not monotonic: performance decreases locally at a budget of 80. The forced
mini-SWE-agent baseline reaches at most 23 fully correct proofs on its plotted curve. The continued bash
agent baseline solved 26.5 problems at similar input token budget. With GPT-5.5-high workers, GitSwarm
solves 28 of 30 problems at a budget of 20 workers and all 30 at budgets of 40 and 80. Note that Best-of-N
baselines (with oracle verifier) also reach the benchmark ceiling at lower token consumptions, so saturating this
benchmark does not establish a unique advantage for GitSwarmFull proof results and compute breakdowns
appear in Appendix D.

These benchmarks show how performance changes with additional inference-time compute. Both, however,
have fixed targets and established evaluation procedures. We next consider open-ended research, where
workers must also decide which experiments to run and how to build on their results.

token’s memory. Another worker revisited the result 49.5 hours later, extended the idea to multiple preceding
tokens, and developed a temporal mixer that entered the final model. The best architecture’s declared
dependencies span 24 commits by 24 workers. The changes made by codex on the other hand involved simply
increasing the width of the attention layer and scaling the training budget. Thus, GitSwarm came up with
more interesting architecture modifications.

The repository also supports reuse across completed searches. In a separate run, we seeded GitSwarm with
the winning commits from three prior independent GitSwarm runs. Workers combined their discoveries and
reduced the inherited best development loss from 2.909 to 2.898 in approximately 28 hours. This run inherited
prior research, so its progress is not directly comparable to an independent run. Full trajectories, experimental
histories and a more detailed discussion of the findings appear in Appendix E.2.

Looped Transformer. We next study Huginn (Geiping et al., 2025), a 308M-parameter transformer with
weight-tied recurrence. Workers must preserve recurrence and remain below 350M unique parameters. A
12-worker swarm uses Codex (GPT-5.5; High effort) workers with a 48-hour budget on one 8 GPU H200 node.

After 26 hours, the swarm reaches a protected-development loss of 3.187, compared with 3.265 for the reference,

thirds of the improvement. Its research history tells a different story from RMT. The winning adapter was
proposed early but rejected after evaluation on 128 examples subset of the full development set. Other workers
re-evaluated it on 512 examples and confirmed the improvement on the full development set. Subsequent
analysis found that the smaller evaluation misranked five of twelve model pairs, compared with one at 512

experiments. We next examine how frequently workers reuse earlier contributions across the benchmark runs.

4
Discussion and Limitations

Our results reveal different forms of compounding inference. In program reconstruction, workers repeatedly
integrate discoveries from different branches into increasingly capable solutions. In mathematical proof,
workers often use previous work to verify and compare candidates without extending the selected proof’s
lineage. The architecture research experiments illustrate both cross-branch synthesis and the value of revisiting
earlier failures: the RMT architecture incorporates mechanisms developed on separate branches, while the
Looped Transformer run recovers an initially rejected idea through further evaluation. Useful computation
therefore need not appear directly in the final candidate’s ancestry; it may also inform which directions are
pursued, rejected, or selected.

Causal attribution. Our dependency and execution-trace analyses establish that workers inspect, reuse, and
accumulate previous work, but do not isolate the resulting performance gains. The mandatory informed_by=
field records worker-declared dependencies, while observed artifact consumption provides evidence of use
rather than causal influence. Conversely, selected-solution ancestry omits potentially useful verification and
candidate comparison. A direct intervention would resume matched runs from the same candidate, with and

11

## Page 12

without access to its preceding research history, under equal remaining compute. Separate interventions would
be needed to isolate the effects of persistence, branchability, and cross-branch dependencies. Our synthetic
experiments demonstrate their operational benefits but do not establish their individual contributions to
benchmark performance.

Evaluation scope. Our results are conditional on the evaluated tasks and budgets. ProgramBench performance
is measured on a fixed 50-task subset out of a total of 200 tasks. The perfect IMOProofBench-Advanced
result is a single run; some independent-sampling and Forced baselines also reach the benchmark ceiling,
and execution conditions differ across some proof comparisons. In AutoResearch, the RMT swarm models
and reference share the same 1.3B-token training budget, whereas the compared single-agent models use
more training tokens. The seeded RMT run additionally inherits earlier research. The recorded Looped
Transformer runs were still in progress, and NanoChat comparisons vary in starting checkpoint and GPU
allocation. GitSwarm improves upon the starting points across all three research tasks, but the results do not
establish superiority over every single-agent configuration.

Computational overhead. Persistent collaboration incurs costs as the repository grows. Workers consume
input tokens inspecting previous contributions, while redundant and unsuccessful episodes can spend compute
without producing accepted work. GPU-backed research adds resource contention and scheduling overhead.
Although performance improves with additional inference-time compute over the tested ranges, understanding
when the benefits of accumulated work outweigh these costs requires longer-horizon evaluations with matched
total compute and wall-clock budgets.

5
Conclusion

We introduced compounding inference, in which intermediate work persists and can be extended across
independent agent episodes. GitSwarm provides a substrate for this process through asynchronous workers, a
shared branchable repository, and explicit cross-branch dependencies, without a central intellectual planner.
Across problem solving and GPU-backed research, we observe extensive reuse of earlier work, including the
synthesis of independent discoveries and the recovery of initially unsuccessful ideas. We view this substrate as
a foundation for long-horizon discovery. It supports a continuing loop in which agents propose ideas, run
experiments, preserve their findings, and use earlier evidence to guide new research. A natural next step is to
train agents with reinforcement learning across diverse tasks within this environment. Rather than rewarding
only the outcome of an individual episode, such training could incentivize contributions whose value emerges
through subsequent work, enabling agents to learn not just to solve problems, but to advance a collective
process of discovery.

Ethics Statement

This work involves no human subjects, crowdsourced annotation, or personal data; all experiments use public
benchmarks (IMOProofBench-Advanced and ProgramBench) and research tasks based on publicly available
research papers. Because GitSwarm lets LLM agents execute code and launch GPU jobs autonomously,

A
Related Work

Our work lies at the intersection of inference-time search, agent memory, multi-agent coordination, and
automated research. These approaches differ in how they preserve intermediate work, support competing lines
of exploration, record dependencies, and decide what to investigate next. Table 1 compares representative
systems along these dimensions.

Inference-time search and reflection. Repeated sampling and compute-aware inference allocate additional
computation to candidate solutions (Brown et al., 2024; Snell et al., 2024). Tree of Thoughts explores and
evaluates alternative reasoning paths (Yao et al., 2023), while Language Agent Tree Search combines tree
search with environmental feedback (Zhou et al., 2024). These approaches preserve intermediate states within
a search. In contrast, GitSwarm preserves partial solutions, executable artifacts, and negative results across
independently scheduled worker episodes.

Other methods retain information across attempts. Reflexion preserves verbal feedback for subsequent
trials (Shinn et al., 2023); ExpeL extracts and retrieves insights from previous tasks (Zhao et al., 2024); and
Voyager accumulates reusable executable skills (Wang et al., 2023). MemGPT manages long-term context
(Packer et al., 2023), while A-MEM links and updates memories as new information arrives (Xu et al., 2025).
These systems establish the value of external memory. Our focus is a shared, versioned contribution history in
which independent workers can pursue competing approaches and explicitly declare dependencies across them.

PDR (Madaan et al., 2025) study inference as an iterative improvement process. Their Parallel-Distill-Refine
method generates diverse drafts in parallel, distills them into a bounded textual workspace, and refines a
candidate over successive rounds. Similarly, Recursive Self-Aggregation (RSA) (Venkatraman et al., 2025)
involves sampling multiple (N) outputs in parallel, curating new contexts by randomly sub-sampling and
collecting K outputs, and aggregating them using an LLM operator. This workflow is then repeated over
successive rounds. PDR and RSA allow inference to accumulate information without continually expanding
the model’s context. SqueezeEvolve (Maheswaran et al., 2026) follows a similar orchestration. GitSwarm
shares the goal of building on earlier computation but uses a different memory model. Rather than repeatedly
compressing drafts into a single workspace, it preserves individual contributions in a shared, branchable
repository. Independent workers choose which previous results to inspect or extend, while each commit
explicitly records its dependencies across branches. GitSwarm also operates entirely at inference time, whereas
Madaan et al. additionally investigate training models to use their iterative improvement operator.

Kim et al. (Kim et al., 2026) extend inference-time scaling to long-horizon coding agents. They summarize each
agent trajectory into a structured record of its hypotheses, progress, and failures. These summaries support
recursive tournament voting over parallel attempts and sequential refinement through Parallel-Distill-Refine
(PDR). Like GitSwarm, their method allows later computation to benefit from earlier attempts. The difference
lies in how that work is preserved and organized. Their approach distills trajectories into compact contexts
for selection and subsequent rollouts. GitSwarm instead preserves individual contributions and artifacts in
a shared, branchable repository. Workers independently choose which contributions to extend, while each
commit explicitly records its dependencies across branches.

Multi-agent coordination. Multi-agent debate improves candidate answers through interaction between model
instances (Du et al., 2023), while Mixture-of-Agents aggregates responses across successive model layers (Wang
et al., 2025). AutoGen supports configurable patterns of agent conversation (Wu et al., 2023). MetaGPT
assigns specialized roles within a prescribed software-development workflow (Hong et al., 2024), and AgentVerse
studies configurable teams and collaboration patterns (Chen et al., 2024). Magentic-One uses an orchestrator
to assign work and revise plans (Fourney et al., 2024).

GPTSwarm represents agent operations and communication as an optimizable computation graph (Zhuge
et al., 2024). Its graph specifies how a multi-agent program executes, whereas ours records how published
contributions accumulate over time. Rather than assigning roles or optimizing a communication topology,
GitSwarm lets homogeneous workers independently choose whether to explore, repair, verify, integrate, or
nominate existing work. Its harness still centrally manages execution and applies deterministic plurality
readout.

Version control for collaborating agents. AgentGit introduces version-control operations such as committing,

branching, and rollback to agent workflows, supporting recovery and alternative execution paths (Li et al., 2025).
CAID uses parallel Git worktrees and branch-and-merge integration for asynchronous software engineering,
with a central manager that plans and delegates subtasks (Geng and Neubig, 2026). SwarmResearch also
runs coding agents on separate Git branches, but uses a Shepherd Agent to direct their search and adjust
parallelism (Virk et al., 2026).

These systems demonstrate how version control can organize parallel agent work. In GitSwarm, the repository
instead serves as a persistent substrate for self-directed contributions. Each accepted commit has a physical
Git parent and must declare its semantic dependencies through informed_by=, including references to work
on other branches. Nomination records remain separate from the contribution graph, so evaluating an existing
candidate does not alter its ancestry.

Concurrent work: Agora. Agora (Zhang et al., 2026), developed in parallel with our work, also investigates
compounding research by self-directed agents over a persistent Git-backed contribution graph. Its workers
operate without assigned tasks or a central planner. Contributions retain their dependencies through Git parent
relationships, including multiple parents, while searchable frontier views and diversity-aware recommendations
help workers navigate the research history.

GitSwarm studies a closely related design space with a different contribution and selection protocol. It
separates each commit’s physical Git parent from mandatory semantic informed_by= references and selects
final candidates through worker nominations and deterministic plurality readout.
Our evaluation also
examines fixed-answer benchmarks, controlled substrate properties, and sustained GPU-backed research,
with separate measurements of declared dependencies, artifact consumption, and selected-solution ancestry.
Agora’s extended weight-transfer study instead emphasizes research diversity and independent verification.
The two studies provide complementary evidence about repository-mediated collective research rather than a
direct performance comparison.

Blackboards and global workspaces. GitSwarm belongs to a long lineage of architectures that coordinate
distributed computation through shared state. Classical blackboard systems such as HEARSAY-II allow
independent knowledge sources to opportunistically read from and contribute to a common workspace (Erman
et al., 1980; Nii, 1986). Global Workspace Theory similarly organizes cognition around multiple specialist
processes whose information can gain access to a shared broadcast workspace (Baars, 1988). Shanahan
developed computational realizations of this principle in cognitive and neural architectures based on competition
and global broadcast (Shanahan, 2006, 2008), and Goyal et al. (2022) brought the idea to modern neural
architectures, allowing learned specialist modules to communicate through a capacity-limited shared workspace.

GitSwarm inherits the shared-workspace principle but changes the temporal and structural role of the
workspace.
Rather than maintaining a transient common state for coordinating computation within a
cognitive cycle or neural forward process, GitSwarm preserves an explicit history of contributions across agent
episodes. The workspace is durable and branchable, and dependencies between contributions are recorded
explicitly, allowing competing lines of work to persist and later recombine. Our focus is therefore not only
coordination through shared state, but the accumulation of reusable computation over long horizons.

Autonomous experimentation and evolutionary search. Karpathy’s AutoResearch repeatedly modifies, trains,
and evaluates a NanoChat model in a single-agent loop (Karpathy, 2026). The AI Scientist automates stages
from idea generation to paper writing (Lu et al., 2024), while AI Scientist-v2 uses progressive agentic tree
search directed by an experiment manager (Yamada et al., 2025). Agent Laboratory organizes literature
review, experimentation, and writing into a staged research workflow (Schmidgall et al., 2025).

AlphaEvolve maintains an evaluated population of programs and uses evolutionary selection for algorithm
discovery (Novikov et al., 2025).
AIRA2 combines agentic experimentation, consistent evaluation, and
asynchronous multi-GPU execution (Hambardzumyan et al., 2026). These systems demonstrate the value of
experimental feedback, persistent candidate pools, and parallel research.

Our question is how independent research episodes can additionally preserve hypotheses, failed experiments,
code, and supporting evidence in an auditable contribution graph, without a central agent selecting each next
experiment. The research histories in Section 3.3 illustrate cross-branch architectural synthesis and the later
reconsideration of initially rejected results. These observations demonstrate reuse, but do not by themselves
establish its causal effect on performance.

Earlier work on autonomous research establishes complementary ways to organize experimental search.
AIRA (Toledo et al., 2025) studies how search policies and operators interact in machine learning research,
while AI Co-Scientist (Gottweis et al., 2025) uses asynchronous agents and tournament-based refinement to
develop scientific hypotheses. The Darwin Gödel Machine (Zhang et al., 2025) maintains an expanding archive
of coding agents, empirically validating modifications that improve the agents themselves. ARTS (Juneja et al.,
2026) uses a central reasoning model to inspect the logs of earlier experiments and choose which node of a
search tree to expand, separating weak hypotheses from flawed implementations rather than ranking nodes by
score. Because this scientist carries the entire search, ARTS condenses the growing history into short written
insights and, in a variant, into the model’s weights via test-time training, and it returns the best validated
node. GitSwarm has no central scientist: independent workers, each starting with a fresh context, retrieve
what they need from a shared version-controlled persistent repository that is never summarized or pruned,
can combine separate branches into a single contribution, and select the final solution through decentralized
nomination when no reliable validation score exists. GitSwarm instead keeps the worker model fixed and
accumulates contributions to an external research task. Its repository preserves competing experiments,
including unsuccessful ones, with explicit dependencies between contributions.

Meta-Harness (Lee et al., 2026) searches over the code of LLM harnesses with a single coding-agent proposer
that reads the source code, scores, and execution traces of all prior candidates from a filesystem. Like
GitSwarm, it exposes the full, uncompressed history for selective retrieval rather than summarizing it. Its
search, however, proceeds in sequential iterations, and every stored candidate is a complete harness, evaluated
on a fixed search set and logged in a predefined per-candidate directory. GitSwarm contributions can instead
be bounded partial work that later workers extend, providing a higher branching factor and thus allowing
more exploration. Branches and explicit dependencies let many asynchronous workers build on one another
concurrently under version control, and beyond a small core layout, workers choose which artifacts to leave.
GitSwarm is also applied across program reconstruction, proof search, and architecture research rather than
to a single class of artifact.

Evaluating autonomous research.
MLAgentBench (Huang et al., 2024), MLGym (Nathani et al., 2025),
ResearchGym (Garikaparthi et al., 2026), and AIRS-Bench (Lupidi et al., 2026) provide environments and
benchmarks for end-to-end machine learning research. MLGym additionally provides an environment for
developing reinforcement learning algorithms for research agents. These works motivate evaluation beyond
fixed-answer coding tasks. Our experiments instead examine how independently scheduled workers accumulate
code and experimental evidence through shared persistent memory.

Comparison by design principles.
Table 2 compares systems along seven properties relevant to compounding
inference: shared memory that persists across agent episodes; durable branches for competing approaches;
self-directed work selection without a central task planner; absence of predefined specialist roles; asynchronous
workers; explicit dependencies across branches; and dependency records that distinguish the physical starting
state from other sources used by a contribution.

These properties are not independent, nor are they a performance ranking. In particular, systems can provide
several of them through different mechanisms. We compare the protocols described in the cited papers, rather
than every configuration their underlying frameworks could support.

Relation to repository-based collaboration.
CAID and SwarmResearch use Git branches to support parallel
work, but organize that work through a central manager or Shepherd Agent. The former delegates dependent
software engineering subtasks; the latter chooses starting points and steers exploration. GitSwarm instead
lets each worker inspect the repository and independently choose what contribution to make.

Agora is closer in its control model. Its workers also choose their own research directions without assigned
roles or a central planner. Both systems preserve intermediate research in a Git-backed contribution graph,
including alternative approaches and unsuccessful experiments. Their dependency tracking and selection
mechanisms differ. Agora represents dependencies through Git parent relationships, including multiple parents,
and provides evidence-aware and diversity-aware views of the research frontier. GitSwarm separates the
physical Git parent from additional mandatory informed_by= references, allowing a worker to build on one
branch while explicitly citing discoveries from others. Workers nominate candidate solutions, and the harness

C
Controlled Tests of Substrate Properties

This appendix gives the full task definitions, interfaces, treatments, settings, and results for the three controlled
tasks summarized in Section 3.1. Each synthetic task isolates a setting in which one property of the shared
substrate (persistence, branchability, or attribution; Section 2.1) should reduce a particular form of repeated
work. All experiments use Gemini-3.1-Pro and three random seeds; Appendix C.4 discusses the scope of these
tests. Symbols such as B, C, D, and k are local to the synthetic tasks; in particular, B denotes the number
of workers in a synthetic run, and C in the Retracted Evidence task counts candidate conclusions, not the
concurrency limit of Section 2.3. The worked examples below use short readable IDs; experimental instances
use random opaque IDs and randomize their display order for each worker.

C.1
Persistence: Hidden Rulebook

Task generation.
The hidden rulebook is a collection of records with opaque IDs. A record is either a fact
containing an integer, or a unary rule containing the ID of one earlier record and an addition or multiplication
to apply modulo 997. For each of the P requested targets, the generator creates an independent chain of D
rules ending in one fact. Solving all targets therefore requires exactly Q = P(D + 1) relevant records. The
remainder of the rulebook consists of disconnected distractor facts and rules. A worker initially sees only the
target IDs. Inspecting a rule reveals its predecessor’s ID but not that predecessor’s contents, so each chain
must be discovered one record at a time (Figure 11).

reduces the rediscovery cost of extending sequential investigations.

C.3
Attribution: Retracted Evidence

Task generation.
The archive contains source notes, derived evidence notes, and candidate conclusions. A
source note states a numerical claim such as “specimen Iona has baseline resonance 22.” A derived note
names a specimen and metric, applies a signed numerical adjustment to one earlier claim, and reports the
result. Its true parent is the unique preceding note whose specimen, metric, and value make this calculation
correct. A conclusion states that one candidate answers one question and names the claim required to support
it. An artifact is valid only if its producer and every artifact in its ancestry remain valid. We choose one
intermediate artifact to be authored by a retracted laboratory and attach multiple downstream branches
to it; all conclusions below it become invalid. For each of the P questions, exactly one of the C candidate
conclusions has a fully clean lineage (Figure 15).

Interface and treatments.
The initial catalog always shows each artifact’s ID, type, and title; conclusion
rows also show their question ID and candidate answer. In the attribution treatment, each row additionally
contains its producer and immediate parent IDs. In the no-attribution treatment, these fields are absent and
workers must recover the lineage from the numerical statements. The prompt does not name the treatment.

read_artifacts(artifact_ids, rationale) returns the full text of the requested artifacts and charges one read per
artifact. submit_answers(answers) submits one candidate for every question, and yield_worker(summary)
ends an episode. Four workers run sequentially; all artifact texts read by earlier workers and all earlier
submissions remain visible. Thus both treatments have persistent observations: they differ in whether explicit
attribution (dependency) metadata is available, not in whether their accumulated observations persist.

Difficulty controls and settings.
Lineage depth L is the number of ancestry levels ending at a conclusion.
Semantic ambiguity A is the number of plausible parent notes with the required specimen and metric at
a parent-selection step; only one of them has the required value. Fan-out F is the number of downstream
branches below the retracted intermediate artifact. All conditions use P = 4 questions, C = 2 candidates
per question, four workers, and three seeds. We sweep one factor at a time (Table 5). The per-worker read
budget is k = ⌈|A|/4⌉, where |A| is the generated archive size, so the combined budget of the four workers is
sufficient to read the complete archive in principle.

Metric.
The primary metric is the fraction of unique archive artifacts read before the first exact submission.
It measures the information-gathering cost of identifying valid conclusions, and distinguishes the ability to
follow recorded dependencies from the cost of reconstructing those dependencies from content.

C.4
Scope of the Controlled Tests

These experiments examine three distinct costs: rediscovering prior observations, retraversing previously
explored states, and reconstructing dependencies between artifacts. They provide controlled illustrations
of why persistence, branchability, and attribution may be useful for compounding inference. They do not
establish that any individual property causes GitSwarm’s benchmark improvements (Section 4). Such a claim
would require interventions on the corresponding property within the full system while controlling for changes
in compute, worker behavior, and the remaining substrate capabilities.

AutoResearch: Additional Details

This appendix complements Section 3.3 with the common research setting (Appendix E.1), the precise task
specifications and compared configurations, full-size hill-climbing figures, and the detailed research records of
the Residual Matrix Transformer (Appendix E.2) and Looped Transformer (Appendix E.3) runs, including the

E.1
Common Setup

Research setting.
In each of the three architecture-improvement tasks, the system is given a description
of an initial transformer architecture and a fixed number of GPUs, and is instructed to make architectural
modifications and hill-climb on a given metric.
The focus is on meaningfully interesting architectural
modifications rather than minor tweaks and hyperparameter changes.
Workers start from an existing
implementation and a task-specific research objective, independently propose modifications, implement
candidate designs, run experiments, and use previous results to guide subsequent work.

Resource coordination.
Unlike mathematical proofs or program reconstruction, these tasks require coor-
dinating expensive experiments under limited computational resources. Workers must coordinate not only
on architecture design but also on resource management: which worker uses how many GPUs to run its
experiments, and which experiments to prioritize when resources are constrained. Workers submit training
and evaluation jobs through a SLURM scheduler and share a fixed GPU allocation (Section 3.3), resembling a
typical research group pursuing architecture research. Their code, experimental results, and research notes
persist in the repository, allowing other workers to inspect and extend previous work.

Evaluation and reporting.
We evaluate progress through the best objective value attained over research
time and, where available, held-out evaluations of the resulting architectures. Because the objective, starting
architecture, research budget, and comparison conditions differ across tasks, we report each task separately
rather than aggregating the outcomes into a single research performance score.

E.2
Residual Matrix Transformer

E.2.1
Task Details

Architecture.
The Residual Matrix Transformer (RMT; Mak and Flanigan, 2025) replaces the transformer’s
residual vector with an outer-product memory matrix: each layer retrieves its input from the matrix through
learned read keys and stores its output back as outer products of learned write keys and values. This lets the
residual stream be scaled independently of parameters and compute.

Task specification.
Starting from the authors’ JAX implementation, the swarm must develop an architecturally
improved RMT that retains a matrix-valued residual stream and has at most 350M parameters, trained from
scratch on a supplied 6.5B-token OpenWebText stream. The search metric is next-token cross-entropy on the
4,873-example protected development set (512 context tokens, one withheld target token); the reference is a
305M RMT trained on 1.3B tokens (development loss 3.158). Final held-out losses, such as the reference’s
3.147, come from a separate held-out evaluation. The task explicitly prioritizes fundamental architectural
changes over hyperparameter or configuration tuning.

Compared configurations.
Besides the two 12-worker GitSwarm configurations with 8 or 4 GPUs, the single-
agent direct GPT and Codex baselines use the same model (GPT-5.6-sol at xHigh reasoning) and the same
72-hour budget on one eight-H200 node. We also examine a GitSwarm run seeded with earlier incumbents
(Appendix E.2.4). Figure 4(a) shows the research trajectories.

Final architectures.
Both GitSwarm runs improve on the reference within its parameter cap and training
budget. The 8-GPU run’s final model combines six mechanisms (Table 6): three general transformer changes

model after the extension (dev 2.894) widens it to rank 64 (Appendix E.2.4). The 4-GPU run converged on
an overlapping but simpler design, tied embeddings, SwiGLU, and a deeper 32-layer stack, with a held-out
loss of 2.894.

How the baselines’ gains differ.
The baselines’ gains were of a different kind. Direct GPT trained longer
(3.0B tokens) and added an auxiliary output decoder, and Codex reached 2.690 mainly by training for 10.1B
tokens, from which about three quarters of its gain came. GitSwarm’s gains, by contrast, come entirely from
architectural changes at the reference training budget, half of them specific to the RMT’s matrix memory,
which is the kind of change the task asks for.

Ideas tried.
Table 7 lists the 19 idea families explored by the GitSwarm RMT run over the 72-hour run and
its extension, with their outcomes. The families range from standard transformer components (gated MLPs,
embedding tying, attention normalization, positional schemes, differential attention) to ideas specific to the
matrix memory (routing along its axes, normalizing it, changing how layers read from and write to it, mixing

Negative results.
The 69 negative commits (58% of the 120) are ideas that their authors published as not
beating their control or the current best model. They were not discarded: the roughly 30% of them later
cited as evidence by other workers compares with 84% of positive commits.

E.3
Looped Transformer

E.3.1
Task Details

Architecture.
The Looped Transformer task uses Huginn (Geiping et al., 2025), a depth-recurrent language
model that splits the network into a prelude, a weight-tied recurrent core, and a coda. The prelude embeds the
input, the core is iterated a variable number of times with the prelude output re-injected at every iteration—an
adapter mixes the current state with the encoded input—and the coda decodes the final latent state, so
test-time compute can be scaled by unrolling more iterations instead of generating more tokens.

Task specification.
Starting from the authors’ official code, scaled to a ∼308M-parameter reference (1,024-
token context, eight recurrences), the swarm must develop an architecturally improved model that keeps
genuine weight-tied recurrent-depth computation, has at most 350M unique parameters, and is trained from
scratch with the reference’s token budget on the same 6.5B-token OpenWebText stream as the RMT task
(Appendix E.2.1). The metric is the withheld next-token loss on the 4,873 protected-development 1,024-token
contexts, evaluated at exactly eight recurrences (reference 3.265); we do not yet report a held-out evaluation
for this task.

Protocol and compared configurations.
Candidates are developed on a ladder of smaller models (52M, 124M,
188M) before full-size training. GitSwarm (12 workers), direct GPT and Codex all use GPT-5.5 High with a
48-hour budget on one eight-H200 node; the runs were still in progress at the time of writing (26 of 48 hours).
Figure 5(a) shows the research trajectories.

E.3.2
Final Architecture and Idea Families

Final architecture.
The best model differs from the reference in one place: the linear adapter that re-injects
the input at every iteration is replaced by a small gated feed-forward network. Because this adapter runs at
every recurrence, it is the component most specific to looped models, and the change adds 27M parameters
(8.7%). The parameter-matched control of Section 3.3, trained with the reference’s size, checks that the gain is
not simply extra capacity. The baselines instead added signals to the recurrent state (a learned per-iteration
embedding for direct GPT; input anchors and step signals for Codex), which helped direct GPT on smaller
models but not at full size; neither baseline has yet beaten the reference.

memory, and changes to the core, readout and objective. GitSwarm used 1,222 GPU jobs and all 64 permitted
protected evaluations, against 324 and 222 jobs for direct GPT and Codex.

Steps on the Solution Path

How the final architecture emerged.
Workers first screened all twelve families in parallel on small models;
within two hours the recurrent-state gate and the feed-forward adapter were the two leading ideas. After
the adapter’s initial rejection was reversed (see the steps below), the two were carried up the ladder side by
side: the gate’s advantage vanished at 124M and 188M, while the adapter won at every rung and reached

mechanisms on top of the adapter, such as attention to the input and parallel feed-forward branches, several
of which beat it on small models but not yet at full size. Nothing has improved on the best model since 9
hours; the later shift to calibration and diagnostics is described in Appendix E.3.4.

Cross-lineage inheritance.
Unlike in the RMT run, the final model’s code comes almost entirely from one
lineage of six commits by six workers; only the first changes code, and the only code imported from elsewhere
is a loss-computation fix written for another branch. Other lineages contributed evidence instead: the rival
gate’s full-set scores defined what the adapter had to beat, and a shared tool for fast proxy measurements
(the second most-cited commit) was used to compare candidates. Counting the commits the best model cites
as evidence through informed_by= edges, its declared dependencies span 89 commits by 89 distinct workers
(98 commits, made between 0.18 and 9.10 hours, if mistyped commit hashes are recovered by unique prefix).

• 124M rung (5.8 h, −0.055 against the reference).

E.3.4
Findings about the Research Process

• Small evaluations misranked models. 128-example evaluations disagreed with the full set on 5 of 12
comparable pairs, and with 512-example evaluations on 15 of 50; a worker measured this itself and the
swarm adopted a 128→512→4,873 evaluation funnel.

• Gains often failed to transfer across scale. The recurrent-state gate, the specialist branches and iteration-
dependent control all lost their small-scale advantage at larger rungs or against a parameter-matched
control.

• Workers checked each other. Besides the reversal of the adapter’s initial rejection (Appendix E.3.3), a later
worker overturned a 128-example win for iteration-dependent control, and four workers independently
ran parameter-matched controls.

• Shared protocols emerged. A fixed set of proxy contexts was used by 257 commits and parameter
matching was discussed in 187; commits that built measurement tools and controls were among the
most cited.

• Work converged, then shifted to diagnostics. The share of architectural commits building on the adapter
rose from 17% in the first three hours to about 90% after nine, which one worker flagged as over-
concentration. After the evaluation budget ran out (20.8 hours), most commits were calibrations and
diagnostics, and 128 of 136 abstentions cited duplicate or already-running work.

• No off-task drift was observed in this run.

E.4
NanoChat

Task and protocol.
Starting from the original NanoChat/autoresearch implementation, workers optimize
validation bits per byte (BPB; lower is better), training each candidate from scratch on one GPU under
the supplied five-minute training clock and fixed evaluation. We analyze GitSwarm job using GPT-6 Astra
at high reasoning with 20 live workers sharing 16 GB300 GPUs. Unlike the RMT task, this task does not
fix parameter count or training-token exposure: architecture, model capacity, optimization, and training
throughput are all research variables. We distinguish the first 24 hours of active allocation from the longer
record, which spans 66.84 allocated hours and 78.48 elapsed wall-clock hours because of requeues. Active time
includes startup, compilation, and API waiting while allocated; it excludes gaps between allocations.

Results.
Within the first 24 active hours, the run improves from 0.992692 to 0.905235 BPB (8.81%),
completing 1,465 successful evaluations of 1,219 distinct train.py solutions, plus 175 failed evaluations. The
incumbent was measured at 23.67 active hours, or 25.15 elapsed wall hours; a strict 24-wall-hour cutoff instead
gives 0.905487. The complete record contains 3,630 successful and 453 failed evaluations, with 2,784 distinct
successful solutions. Its best observation is 0.898671 (9.47% below the reference), but this is an extension
result, not a 24-hour result or a separately held-out test score.

Architecture at the 24-hour cutoff.
The incumbent retains eight transformer layers but widens the residual
stream from 512 to 768 dimensions, uses eight 96-dimensional attention heads, and shortens local attention
windows from 1,024 to 512 tokens while retaining full-context layers. It reallocates feed-forward capacity from
uniform fourfold expansion to fourfold expansion in the first four layers and eightfold expansion in the last
four. A new 2,097,152-row table supplies hashed causal bigram and trigram embeddings, sharing storage
between the two feature types. Query/key normalization moves before rotary embedding. These changes
are accompanied by activation scaling, optimizer changes and a custom training-head implementation. The
resulting model has 1,723.9M parameters versus 50.3M initially; 1,610.6M belong to the lexical table. It trains
on 547.9M reported tokens versus the reference’s 728.2M. Thus this is substantive architecture and capacity
search, but not an architecture-only, equal-parameter or equal-token comparison.

Interpretation of these behaviors.
These episodes show observed reuse and revision of experimental evidence,
including contributions that produced neither a new architecture nor a best score. This run explicitly
assigned experimenter/synthesizer and critic/verifier roles at a configured 3:1 ratio: it supports adaptive work
selection within those roles, not specialization without predefined roles. The traces document dependencies in
experimental judgment, which need not be code-inheritance edges. They do not establish that shared memory
caused the performance gain or identify each reused idea’s contribution; those claims require an appropriate
comparison or ablation.

How the architecture emerged.
Figure 6(b) condenses these developments. Early parallel tests establish

and locality are then combined. Hashed bigrams open a second capacity axis, and their combination with

The selected path includes locally inconclusive and memory-oriented steps, not just successive best-score
observations. This explains how the final combination can emerge through measured branches without
assuming that every isolated improvement transfers additively.

E.5
Findings Across Research Tasks

The three studies extend the evaluation from benchmarks with well-defined target solutions to multi-hour
research tasks requiring architectural decisions, experimental feedback, and shared GPU resources, and they
provide complementary evidence: RMT includes completed held-out evaluations of improved candidates;
the Looped Transformer shows improvements during the recorded development trajectories; and NanoChat
examines research from multiple starting points under different resource allocations.

An improving research trajectory does not by itself establish how much of that improvement comes from access
to previous workers’ discoveries, nor does improving a research objective reveal which earlier experiments
informed subsequent research decisions. The repository provides a mechanism for preserving experimental
artifacts and coordinating subsequent work, but attributing a specific architectural improvement to earlier
contributions requires analysis of the corresponding execution traces and experimental dependencies (see also
the discussion of causal attribution in Section 4).

Selected-solution ancestry.
A worker may depend on only a few immediate sources while indirectly inheriting
work from many earlier workers. Each contribution records its Git parent and any additional commits named
in its informed_by= field (Section 2.2). Recursively following both kinds of edge from the selected solution
yields the part of the contribution graph that was carried into that solution, rather than merely produced
somewhere during the run; the task root and nomination records are excluded. On ProgramBench this
ancestry covers most of the contribution graph (Figure 7), so repeated local composition from a few sources
produces a broad final ancestry; selected proofs retain a much smaller share.

Coverage by budget.
Figure 7 reports, for each budget (B100–B500 on ProgramBench, B20–B160 on

F.3
Collaboration Workflows

The contribution graph also exposes distinct, problem-adaptive patterns of collaboration that emerge in
GitSwarm runs, complementing the task-level work mix in Section 3.5 (Appendix G.1). A workflow archetype
describes the dominant way that contributions are organized in one run. It is inferred from the commit
graph, informed_by= edges, worker actions, and the semantic role of each contribution. It is not a role
schedule imposed by the prompt. Figure 9 illustrates two representative ProgramBench runs. One exhibits late
integration, in which separate lines of implementation work are subsequently combined. The other illustrates
search-and-pivot (search and redirection), as workers develop alternative approaches over an extended run.

Late integration and divide-and-conquer.
In Delta B100 (Figure 9(a)), several branches improve different
parts of a candidate before a broad rendering synthesis combines diff highlighting, submodule-log behavior,
conflict handling, and other independently developed repairs at 80% of the run. The selected candidate at 92%
incorporates further line-number and raw-line inspection work. This is late integration because the decisive
candidate depends on several mature branches rather than one steadily refined line. Divide-and-conquer runs
such as Pandoc B100 use a related but more specialized pattern: separate groups develop document structure
and inline syntax on one branch and output modes and code-block handling on another before the branches
join.

Search-and-pivot.
The Cheat B500 run (Figure 9(b)) shows a different, search-and-pivot workflow. Workers
spend the first 35% of the run mainly on CLI, configuration, YAML, and frontmatter behavior. Four renderer
experiments then appear within one percentage point, covering JSON, style palettes, Go, and HTML/XML,
and are quickly combined. CLI and configuration work continues until about 57%, while renderer work
becomes the dominant selected lineage and ends in a final renderer synthesis. The pivot is a gradual change
in the dominant search direction, not an abrupt replacement of all earlier work.

Caveats.
These examples are intended to make the dependency graphs interpretable. The labels summarize
observed graph structure; one graph can contain more than one pattern, and the dominant pattern for the
same problem can change with the compute budget. The examples therefore explain mechanisms seen in the
traces rather than define an exhaustive set of mutually exclusive strategies or claim that a pattern is the best
possible workflow for a task.

G.2
Worker Episode Outcomes and System Health

Episode outcomes by budget.
Figure 22 shows that the different work mixes of the two benchmarks do not
reflect a general collapse into failed work. Roughly three quarters of all ProgramBench worker episodes end
in a contribution commit at every budget, while abstentions remain spread through the run. The exact
contribution share is partly shaped by five-worker concurrency, but the persistence of repair, expansion, and
synthesis (Figure 10) matters more than the precise value. IMOProofBench-Advanced has more selection
outcomes and more no-action or invalid episodes, consistent with its smaller active proof frontier.

Unsuccessful charged episodes.
Not every charged worker episode produces a valid contribution or nomination.
Across the 200 ProgramBench B100 runs, 615 of 20,000 charged episodes (3.1%) produce no accepted action.
Of these, 515 fail candidate-publication or required-artifact validation, 79 fail nomination validation, and 21
terminate without a valid action because of API failures, turn limits, or protocol violations.

Coordination overhead.
These unsuccessful charged episodes are distinct from voluntary abstentions, which
are replaced without consuming the charged budget (Section 2.3). Both nevertheless consume resources, so the
effective cost of collaboration includes unsuccessful work, redundant work (Appendix G.4), and inspection of
shared history (Appendix G.5). The execution system must also manage asynchronous publication, validation,
and access to in-flight activity. Detailed worker-outcome and coordination statistics help characterize this
overhead separately from the benchmark performance of accepted contributions.

G.3
Voting Dynamics and Selection Timing

Workers may nominate an existing candidate rather than publish another contribution (Section 2.3). We
analyze compounding nominations over normalized worker-spawn progress (Figure 23) and measure when
the eventually selected candidate is first committed relative to the first nomination (Figure 24). Section 3.5
summarizes the timing results; this subsection gives the per-budget details. Figure 23 shows that selection is
autonomous rather than a fixed final phase. More compute produces more comparisons and votes in both
benchmarks, but their timing differs.

ProgramBench.
Nominations are concentrated toward the end of ProgramBench runs. Workers continue
constructing, repairing, and integrating implementations for much of the available budget, followed by a clear
terminal voting pulse of candidate comparison (Figure 23(a)). The first vote moves from 68.4% of normalized
progress at B100 to 16.1% at B500, mainly because the total run grows from about 122 to 599 episodes
while voting starts after a similar absolute amount of work; a substantial selection pulse still remains near
termination at larger budgets. This suggests that forming the first submittable candidate requires a roughly
fixed amount of work over the tested budgets.

Figure 24(a) connects voting to candidate construction. The exact ProgramBench winner is produced late,
at 93.1–98.0% median progress, only 8–11.5 worker episodes before termination, consistent with continued
refinement and integration throughout the run. Construction continues near the budget boundary, and the
winner is usually a final repair or integration that inherits older work. Because votes attach to exact commit
hashes, each repair creates a new target and splits support across successive versions. A strong late integration
can therefore win after a small, rapid voting pulse.

IMOProofBench-Advanced.
The proof-solving runs follow the opposite pattern (Figure 23(b) and Figure 24(b)).
Nominations begin much earlier, continue over a larger fraction of the run, and accumulate almost linearly
after startup. The median first nomination (voting onset) moves from 32.5% of worker-spawn progress at
B20 to 4.0% at B160, with the intermediate budgets falling in between. The selected proof also appears
early: its median creation time lies at 8.6–17.5% of normalized progress across the tested budgets. Mean
nominations per problem rise from 9.1 at B20 to 115.6 at B160. Later workers mostly compare and ratify
that early candidate.

Relation to selected-solution ancestry.
Nomination timing thus matches the different accumulation regimes.
These differences help explain the contrasting selected-solution ancestry reported in Section 3.4 (Figure 7).

G.4
Voluntary Abstention and Redundancy

Workers may explicitly abstain when their intended contribution is already covered by published or in-flight
work, or when no useful nonredundant change remains; voluntary abstainers are replaced without consuming
the charged budget but still incur token costs for the inspection and reasoning they perform before abstaining
(Section 2.3). By contrast, invalid actions, invalid nominations, no-action exits, and system failures do consume
a slot; invalid and no-action episodes are shown in the Invalid / no action class of Figure 22, separate from
voluntary abstentions. Section 3.5 summarizes the main redundancy findings; this subsection reports the
underlying statistics and the calibration of abstention judgments.

Redundancy rates and collision sources.
A worker declares redundancy when it abstains because equivalent
work is already committed or in flight. Figure 25 shows that declared implementation redundancy stays
near one ProgramBench worker in six across budgets, but remains below 2.7% on IMOProofBench-Advanced.
Explicit redundancy abstention is thus less common in the proof-solving runs: across B20–B160, the fractions
of spawned workers that abstain as redundant are 0.65% (B20), 1.22% (B40), 1.49% (B80), 2.62% (B120), and
2.39% (B160). Figure 26 explains much of this difference. ProgramBench abstainers usually cite overlapping
work that is still in flight, so many ProgramBench abstentions arise from redundant concurrent work. Proof
abstainers instead usually cite a completed, already published proof rather than concurrent in-flight work: of
the 273 IMO redundancy cases, 268 include committed evidence and only three cite in-flight work alone.

Asynchronous overlap on ProgramBench.
The ProgramBench cases usually arise from asynchronous overlap.
Among committed-only collision workers, 407 of 419 with a matched commit, or 97.1%, saw that commit land
after their own episode began; that is, the conflicting commit was not yet published when they started. They
were not idle while waiting. Of these workers, 86.7% edited files, 98.8% built a candidate, 99.0% ran tests,

48

## Page 49

and 95.1% probed the oracle. In 71.5% of cases, the worker had seen the eventual committer’s public scope
and continued working; a smaller subset explicitly planned to wait or refresh the graph before committing.
The usual behavior is parallel work (editing, building, testing, and probing) followed by a late check of the
durable result, after which the worker stops; abstention therefore prevents a duplicate commit but not the
computation already spent. Proof abstainers instead stop after a median of five to seven tool turns once they
find a completed candidate (Figure 26(c)).

Token cost.
The resource cost follows the same difference. As shown in Figure 27, ProgramBench abstainers
consume about 6–7% of both input and output tokens across the analyzed budgets. Explicit proof abstainers
consume only 1.2–2.8% of input tokens and 0.3–0.8% of output tokens. These values do not include the larger
set of no-action, invalid, and selection-related proof episodes.

Calibration review on ProgramBench.
We calibrated the ProgramBench judgments with a score-blind review
of all 422 committed-only collisions and five pre-registered in-flight-only cases per problem and budget, for
1,422 abstention traces in total: 289 at B100, 315 at B200, 346 at B300, and 472 at B500. The review packet
contained the worker’s scope, terminal rationale, final public in-flight state, cited peer outcomes, later commits,
and selected-candidate ancestry. Common cases were resolved from this evidence, and cases with failed peer
paths, unresolved references, or questionable probes received semantic review. The review labels are defined
as follows:

• Justified: the cited work materialized and covered the intended contribution.

• Premature but recovered: the cited path failed, but later work restored the capability.

• Premature and unrecovered: the cited path failed and later work did not restore the capability.

• Spurious: invalid or unstable evidence was mistaken for redundancy.

• Ambiguous: the trace does not identify a concrete claim that can be checked.

Figure 28(a) reports the resulting calibration by budget. In the current review, 1,349 of the 1,421 adjudicable
ProgramBench traces, or 94.9%, are classified as justified.

Trace-evidence audit on IMOProofBench-Advanced.
The IMO audit finds a named pre-existing commit or a
named peer that later committed in 269 of the 273 redundancy cases (Figure 28(b)). This is a trace-evidence
check, not a mathematical equivalence judgment. It establishes that the cited work existed or materialized,
but not that two proofs are mathematically equivalent, that the cited proof is correct, or that abstaining
workers correctly assessed the cited proofs or their own potential contributions.

Interpretation.
The two panels of Figure 28 answer different questions: the ProgramBench review assesses
whether the cited work covered the intended contribution, while the IMO audit checks only whether the named
evidence existed. The high ProgramBench rate shows that abstention usually prevents duplicate commits,
while the few unrecovered cases expose its main risk.

Asynchronous versus synchronous execution.
The default scheduler launches a replacement worker whenever
a worker slot becomes available. The synchronous variant instead executes barriers of five workers: it waits for
every worker in a five-worker wave to finish before launching the next wave. Synchronization changes the mean

latency. Under these conditions, asynchronous execution therefore reduces latency with a small observed
difference in mean score; the experiment does not establish statistical equivalence between the two schedules.

Global component

You are an autonomous worker in an asynchronous search for the best solution to the user's query, collaborating with other workers through a

shared Git repository.

You work autonomously in your own Git worktree within a persistent repository shared by all workers. The repository represents a graph of

candidate solutions. Each graph-expansion commit adds one candidate node.

A candidate's Git parent identifies the repository state from which it was created. Its \`informed_by=\` provenance identifies the earlier commits

this worker directly relied on when developing the candidate. These are different relationships: the Git parent records physical ancestry;
provenance records semantic influence.

The swarm is a discovery process: workers expand and explore this graph in search of the best solution. A candidate node need not settle the

problem permanently. It may instead be a useful stepping stone that later workers inspect, test, criticize, repair, extend, combine, or
replace. Nevertheless, every graph-expansion node must preserve the task-specific structure and artifacts required to stand as a candidate
answer if inspected on its own.

There is no mutable current-best solution and no exclusive selector. Any worker may inspect the graph and nominate one existing candidate by

creating a rationale-bearing nomination commit. Each valid nomination contributes exactly one vote. When the run ends, the candidate
with the most votes is the system output. Equal vote totals are resolved deterministically by lexicographic full commit SHA. If the run
ends without a valid nomination, no candidate solution has been selected and the system falls back to the repository root.

Commands within one response execute as a batch. Their combined stdout and stderr are returned in the next message. Use as many turns as

necessary, and wait for command output before making decisions that depend on it.

Follow the workflow below. Do not branch, edit tracked files, declare a nomination, commit, or abstain before completing the preceding

ProgramBench addendum

# ProgramBench task-specific addendum

The goal is to create a new, original codebase whose compiled executable reproduces the behavior of the provided reference program. The

behavior is to be inferred from the bundled documentation and by running and interacting with the execute-only reference. The final
output must include a \`compile.sh\`. ProgramBench runs it and grades the resulting \`./executable\` against a large hidden test suite.
Repository prose alone is not graded.

## Candidate-node invariant

Every graph-expansion commit is a candidate node. Its tree must contain a self-contained, executable \`compile.sh\` that produces \`./executable\`

in the repository root. This applies to every type of graph-expansion contribution. Every candidate node must retain the structure of a
runnable ProgramBench submission.

The compiled candidate must not copy, wrap, execute, link, or otherwise depend on the reference program at runtime. Generated executables

must not be committed.

A best-solution nominator compares existing candidate nodes. Its nomination-record commit is ballot metadata rather than a candidate. It may

add or update only \`BEST_SOLUTION.md\` and must otherwise preserve the nominated candidate's tree.

## Reference executable

The execute-only reference program is available as \`./executable_orig\`. You may run it and observe normal program behavior, including stdout,

stderr, exit status, and timing. You MUST NOT read, copy, hash, disassemble, decompile, or otherwise inspect its bytes.

The reference is available only during development and is absent during grading. Every candidate and its \`compile.sh\` must therefore be fully

self-contained.

## Worker inheritance and builds

A worker branch inherits the tracked tree of its selected Git parent, including source files, collaboration artifacts, and \`compile.sh\`. Built

executables are untracked and are not inherited. Rebuild a candidate from its committed source when testing it.

Each worker receives a fresh \`./executable_orig\`. \`./baseline_executable\` may hold a candidate built from the worker's starting commit, while

\`./executable\` is reserved for the candidate built from the worker's current tree. Both are untracked build artifacts.

When comparing several candidate nodes, build each one in a separate private temporary directory or worktree so their sources and build

products do not contaminate one another.

## Investigation and validation

Differential testing is one available way to investigate and validate behavior. When using it, compare candidate and reference behavior on the

same inputs, including stdout, stderr, exit status, timing when relevant, and exact formatting.

Bundled documentation and examples provide useful evidence but may not cover hidden behavior. Valid and invalid flags, malformed input,

empty and large input, Unicode, boundary cases, and combinations of modes may expose discrepancies. Compare against inherited or
alternative candidates as well when regression detection or candidate nomination requires it.

Claims in \`MY_THOUGHTS.md\`, \`EVALUATION.md\`, \`BEST_SOLUTION.md\`, and other collaboration artifacts should distinguish

observed evidence from inference. Do not claim coverage that was not performed.

Sequential shell interaction for Gemini-3.1-Pro.
Gemini-3.1-Pro workers receive the extension below at the
end of their system prompt. In pilot runs without it, Gemini workers often issued an entire contribution
workflow (inspection, scope announcement, gs_fork, file writes, and git commit) in a single response,
sometimes predicting command outputs and branching from a guessed commit SHA. When gs_fork then

additions constrain how and when shell commands run (for example, scripts and tests can run only after
branching); the graph, scope, dependency, and nomination rules are unchanged.
