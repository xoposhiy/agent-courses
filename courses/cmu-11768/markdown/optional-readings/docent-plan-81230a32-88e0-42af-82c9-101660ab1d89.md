## Step 1: Why does one model fail a Terminal-Bench task that the other model solves?

## Behavior
This collection holds Terminal-Bench runs of the terminus-2 agent with two models, GPT-5.1-codex and GPT-5-codex, with about three attempts per model on each of 89 tasks. Overall, GPT-5.1-codex passes 27% of scored runs against GPT-5-codex's 40%, and it hits the agent time limit in half its runs. We want to understand, run by run, why a model fails a task that the other model has shown can be solved: for example a wrong approach, a misunderstanding of the spec, an unverified final answer, or time spent on long-running or stuck commands.

## Measurement
We pair every failed run (reward 0, including timeouts) with a successful run (reward 1) from the other model on the same task. If the other model passed that task more than once, a fixed-seed hash picks one success, so the pairing is reproducible. Runs with no reward (harness failures such as cancellations or missing reward files) are excluded. A judge model reads both full transcripts, along with each run's reward and exception, and writes a short paragraph explaining the root cause of the failure, contrasting it with what the successful run did and citing both transcripts. It also gives a one-line cause summary. Results are grouped by model: one step explains GPT-5.1-codex's failures and another explains GPT-5-codex's.

## Step 3: Pair each failed gpt-5.1-codex run with a gpt-5-codex success on the same task

### DQL query

```sql
WITH scored AS (
  SELECT id, metadata_json->>'task' AS task,
    metadata_json->'agent'->>'model_name' AS model,
    CAST(metadata_json->'scores'->>'reward' AS DOUBLE PRECISION) AS reward,
    COALESCE(metadata_json->>'exception', 'none') AS exception
  FROM agent_runs WHERE metadata_json->'scores'->>'reward' IS NOT NULL
),
pairs AS (
  SELECT f.task, f.id AS failed_run, f.model AS failed_model, f.reward AS failed_reward,
    f.exception AS failed_exception,
    s.id AS successful_run, s.model AS successful_model, s.reward AS successful_reward,
    -- one deterministic success per failed run
    ROW_NUMBER() OVER (PARTITION BY f.id ORDER BY md5(CONCAT(s.id, 'pair-v1'))) AS rn
  FROM scored f JOIN scored s ON s.task = f.task AND s.model <> f.model
  WHERE f.reward = 0 AND s.reward = 1 AND f.model = 'openai/gpt-5.1-codex'
)
SELECT task, failed_run, failed_model, failed_reward, failed_exception,
  successful_run, successful_model, successful_reward
FROM pairs WHERE rn = 1
```

## Step 8: Split failure explanations into batches of 20 per failing model

### DQL query

```sql
SELECT failed_model, batch_index, COUNT(result_id) AS n_explanations,
  array_agg(result_id ORDER BY result_id) AS explanations
FROM (
  SELECT CASE WHEN rrl.reading_id = '$2' THEN 'gpt-5.1-codex' WHEN rrl.reading_id = '$4' THEN 'gpt-5-codex' END AS failed_model,
    rr.id AS result_id,
    -- batches of 20 explanations per failing model
    (ROW_NUMBER() OVER (PARTITION BY rrl.reading_id ORDER BY rr.id) - 1) / 20 AS batch_index
  FROM reading_results rr JOIN reading_result_links rrl ON rrl.result_id = rr.id
  WHERE rrl.reading_id IN ('$2', '$4')
) AS subq
GROUP BY failed_model, batch_index
ORDER BY failed_model, batch_index
```
