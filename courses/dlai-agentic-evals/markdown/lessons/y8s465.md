[01:57] Now, choose evaluators for the three Northwind requirements.

[02:01] First, every product mentioned in an agent response should exist in
the catalog. is your source of truth, so this is a code evaluator.

[02:10] If the customer asks for a jacket and the agent recommends a product
that is not in the catalog, the answer may sound reasonable,

[02:16] but the product does not exist.

[02:17] The evaluator can compare the product names or IDs in the response
with the catalog. The check passes if every mentioned product exists.

[02:25] If the response mentions a product that is not in the catalog,
it fails. You don't need an LLM to decide that.

[02:31] The catalog comparison determines the result.

[02:35] But a response can mention only real products and still fail to answer
the customer's question.

[02:40] For example, the customer might ask which shoes are
best for rainy weather,

[02:43] and the agent might list real products without explaining
which ones are waterproof or appropriate for rain.

[02:49] The products exist, but the response may not answer
the actual question.

[02:53] To evaluate that, you need to interpret the customer's question
and the agent's response together.

[02:59] This is a good place to use a built-in correctness evaluator.

[03:02] Phoenix provides a CorrectnessEvaluator for common response quality
judgments like accuracy, completeness, and logical consistency.

[03:10] You provide the customer question and the agent response, and the
judge decides whether the response correctly answers the question.

[03:17] So now you have two checks: one code evaluator that asks,
"Are the products real?"

[03:22] and one correctness judge that asks, "Did the response answer the
customer's question?"

[03:27] But the Northwind agent has another requirement that general
correctness does not fully capture, which has to do with scope.

[03:33] It can answer product and catalog questions, but it should not look up
orders, process returns, issue refunds, check shipping status,

[03:41] or access other support systems.

[03:43] If a customer asks, "Can I return this after 60 days?" the agent
should not invent a return window or ask for an order number.

[03:51] It should simply explain that it cannot help with returns.
A general correctness evaluator may not know that boundary.

[03:57] It might see a fluent, helpful-sounding return answer
and treat it as acceptable.

[04:02] But for Northwind, that response is outside the agent's capabilities.
That means this requirement needs a custom LLM judge.

[04:09] You'll build that judge using the rubric structure from
earlier in the module.

[04:13] Start with the role: the judge is evaluating whether a Northwind
customer-support response stays within the agent's capabilities.

[04:21] Then, define the criteria: a compliant response stays within product
and catalog support.

[04:26] If the customer asks for something outside those capabilities, a
compliant response says that Northwind cannot help with that request.

[04:33] A non-compliant response invents a process or capability
that the agent was never given.

[04:39] That could be a return policy, a refund process, a shipping lookup,
or a support channel that does not exist in the provided information.

[04:47] Next, provide the inputs. For this evaluator,
the judge needs the customer's question and the agent's response.

[04:53] Put them in a clearly labeled data block so the judge knows exactly
what it is evaluating. Then add reviewed development examples.

[05:01] Choose examples that clarify the boundary between compliant
and non-compliant responses.

[05:06] For example, one compliant response might say, "I can help with
product and catalog questions, but I can't process returns."

[05:13] A non-compliant response might say, "You have 90 days to return the
item," even though Northwind never provided that policy.

[05:21] Finally, constrain the output. Ask for one label:
COMPLIANT or NON_COMPLIANT.

[05:26] Fixed labels make the results easier to compare with reviewed labels,
and easier to filter in Phoenix.

[05:32] Once you have the three evaluators, run them on the development cases
and save each result as a separate annotation.

[05:38] That part is important because a response can pass one requirement
and fail another. Suppose a customer asks about returning an item.

[05:45] The agent mentions only real Northwind products,
It gives a response that sounds complete and helpful,

[05:51] but it also invents a return process that Northwind does not support.

[05:54] The product_exists evaluator may pass, as well as the correctness
evaluator, but the policy_compliance judge should fail.

[06:01] If you collapse those results into one overall score,
that policy failure can disappear.

[06:06] Separate annotations let you see which requirement failed and
which responses need inspection.

[06:12] Before relying on the policy compliance labels,
validate the custom judge.

[06:17] Run it on the held-out set,

[06:18] and compare its COMPLIANT and NON_COMPLIANT predictions with the

[06:24] Use recall to see how many actual policy violations the judge caught.

[06:28] Check precision to measure how often its policy
violation flags were correct,

[06:32] and use Cohen's kappa to check how much the judge agrees with the

[06:39] But don't stop at the metrics. When the judge and reviewer disagree,

[06:45] Read the customer question, the agent response,

[06:52] What if the judge missed that the response invented a refund process,

[06:57] or maybe the rubric did not make the capability boundary clear enough?

[07:01] A disagreement does not automatically tell you which side is right,

[07:06] If you revise the rubric based on those disagreements,

[07:11] then test the revised version on fresh reviewed cases when you can.

[07:15] Once a case has influenced the rubric, it is no longer a clean

[07:21] Keep the same discipline you used earlier in the module.
